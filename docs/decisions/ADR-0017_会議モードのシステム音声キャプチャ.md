# 0017. 会議モード: システム音声キャプチャ方式（ScreenCaptureKit 先行スパイク）

- ステータス: **採用**（実機 macOS 26.5 で go ── 未署名でシステム音声キャプチャ成立・更新後はサイレント拒否でなく検出可能な再プロンプト）
- 日付: 2026-06-27
- 関連: [ADR-0011](./ADR-0011_配布は未署名dmgでCloudflareとReleases.md)（未署名配布・$99 署名判断）、[ADR-0007](./ADR-0007_要約llamaを別バイナリsidecarに分離.md)（ggml 衝突＝別バイナリ sidecar）、[ADR-0003](./ADR-0003_MLをRust単一ランタイムに集約.md)（Rust 単一ランタイム）

## Context

Phase 7「会議モード」は **会議相手（Zoom/Meet/Teams のリモート参加者）のシステム音声をローカルで取得 → 文字起こし**する機能。
Granola / Fireflies への競合対抗の核だが、ロードマップは Phase 7〜9 に **「スパイク → ADR → 実装」ゲート**を課している
（faster-whisper × Metal 非対応の教訓＝性能/互換の前提は断定前に裏取り）。

本機能の **load-bearing な前提**は「音を録れるか」ではなく:

> **未署名（＝実質 ad-hoc 署名）の `.app` で macOS 26.5 のシステム音声キャプチャが成立し、TCC 許可が
> 実用に耐えるか。特に更新（再ビルド）後に許可が "クリーン再プロンプト" か "サイレント拒否" か。**

これが [ADR-0011]（未署名配布・$99 署名は規模拡大時に判断）の判断を**前倒しさせるか**を決める。

## 候補（リサーチ: 8 エージェント Workflow + 3 観点の敵対的検証, 2026-06-27）

| 方式 | API | 最低 macOS | TCC | Rust 成熟度 | Zoom/Meet/Teams 実績 | 判定 |
|---|---|---|---|---|---|---|
| **ScreenCaptureKit** | `SCStream`+`capturesAudio` | 13+ | 画面収録（`kTCCServiceScreenCapture`。26 で画面/音声分離も**音声専用でも画面収録を要求**） | **高**（`screencapturekit` v8・音声 first-class） | **あり**（Scripta=whisper.cpp+SCK が ad-hoc 配布で実証） | **先行スパイク** |
| Core Audio process tap | `CATapDescription`+`AudioHardwareCreateProcessTap` | 14.4+ | **より軽い** `kTCCServiceAudioCapture`（音声専用） | 低〜中（`objc2-core-audio`・手組み多い） | ⚠️ 26.5 で「数分後に全ゼロ PCM」「Teams が無音」報告 | **Plan B** |
| HAL 仮想デバイス（BlackHole 等） | kext/ドライバ | — | — | — | — | **却下**（ドライバ導入＝$0/未署名と矛盾） |

仮想デバイスは北極星（$0・追加インストールなし）と矛盾するため却下。

## Decision（暫定）

### 1. ScreenCaptureKit を先行スパイク、Core Audio tap は「計測でトリガーされた時だけ」の Plan B

スパイクの仕事は load-bearing 変数（未署名×TCC）を**最小の交絡**で確定すること。SCK を選ぶ理由:
- **同型の動く前例**（Scripta: whisper.cpp + SCK・ad-hoc 署名・GitHub Releases + xattr）＝失敗時に原因が切り分け可能。
- **成熟した Rust 音声バインディング**（`screencapturekit` v8、`SCStreamOutputType::Audio`）。
- **会議アプリ実績**（Teams 含む）。

Core Audio tap は TCC が軽い利点があるが、26.5 固有の無音バグが 2 件（全ゼロ PCM・Teams 無音）あり、
無音が出たとき「TCC 拒否 / 全ゼロバグ / Teams 非互換」の **3 失敗モードが 1 症状に潰れて切り分け不能**になる。
→ SCK で許可ペインが許容できない（会議メモに画面収録は重い）と**計測で**判明した時のみ Plan B を起こす。

> ⚠️ 軽い `kTCCServiceAudioCapture` ペインは **SCK では得られない**（SCK は音声専用でも画面収録ゲート）。
> スパイクハーネスは Screen ハンドラ＋2x2 ダミー映像を引くので**構造上 Screen Recording 確定**。
> 「どちらのペインか」は問わない。問うのは「会議メモアプリに Screen Recording 許可は許容できるか」だけ。

### 2. アーキテクチャ: 本体 `.app` 内**インプロセス Rust**（bare sidecar 不可）

- `src-tauri` 側（既存 `mic.rs` の隣）に置く。OS/CoreAudio 依存は UI 非依存コア `mojiroku-core` に入れない（`mic.rs` と同方針）。
- **bare Mach-O sidecar（`mojiroku-llm`/`mojiroku-mcp` 型）は不可**: macOS 26.1 で非バンドル実行ファイルは
  Privacy 一覧に出ず、子プロセスの許可は親 `.app` に帰属して TCC 帰属が崩れる。listable なバンドル ID で動かす。
- ggml 衝突（ADR-0007）は無関係（SCK は ggml 非依存）→ whisper-rs と同居して安全。
- **デュアルトラック**: システム音声（相手・SCK・`excludesCurrentProcessAudio=true`）＋ マイク（自分・既存 cpal）。
  「自分 vs 相手」は**強い話者分離の事前情報**（sherpa-onnx を補完）。
- SCK は 48k stereo f32 で来る → 既存 rubato（`mojiroku-core/audio`）で 16k mono 化。

## 未署名×TCC の知見（高確度・機構レベル）

- Apple Silicon の「未署名」＝**実質 ad-hoc 署名**（Tauri 既定）。TCC は ad-hoc を **cdhash でキー**する。
- ad-hoc `.app` でも**ダイアログは出て Allow でき、許可後キャプチャは動く**（bare 実行ファイルは 26.1 で一覧非表示バグ→bundle 必須）。
- **再ビルド/更新ごとに cdhash 変化 → 旧許可が不一致**。固定インストール済みなら再起動を跨いで残るが、**.dmg 更新ごとに再付与**が要る。
- **★ 計測でしか分からない核心**: 更新後に「クリーン再プロンプト（許容可）」か「**サイレント拒否**（トグル ON のまま無音録音＝致命的・要 `tccutil reset`）」か。
- $0 dev-loop 緩和: 無料 Apple Development（Personal Team）ID は Apple 発行＝Team ID 持ち→安定 DR→再ビルドで許可が残る可能性（ローカル反復用・配布不可）。

## スパイクハーネス（`spikes/meeting-audio/`）と現時点の確認

- `screencapturekit` v8 + ad-hoc `.app`（`com.daichi0812.mojiroku-spike`）。`package.sh` が毎回 cdhash を変える（再ビルド計測用）。
- ✅ **macOS 26.5 で build/link/run 確認**（コンパイル・clean deep ad-hoc 署名・dyld ロード成功）。
- ✅ `SCShareableContent::get()` が **TCC ゲート点**であることを確認（権限無しの親プロセスで `NoShareableContent("...declined TCCs...")` をクリーンに返す＝クラッシュなし・エラー分岐 OK）。
- **配布知見（重要）**: `screencapturekit` の build.rs が出す Swift ランタイム rpath（`-Wl,-rpath,...`）は
  **`cargo:rustc-link-arg` が依存先→最終バイナリへ伝播しないため消費側に効かない**。消費側 `build.rs` で再発行が必要。
  焼いた rpath は **Xcode ツールチェーン path（ユーザー機に無い）**を含む → 実装時は **Swift Concurrency ランタイムの
  `.app` 同梱（@executable_path/../Frameworks）か OS 解決**を検証する必要がある（未署名配布の追加タスク）。

## 計測結果（実機 macOS 26.5 / Apple Silicon, ユーザー実施 2026-06-27）

ad-hoc 署名の最小 `.app`（`com.daichi0812.mojiroku-spike`）を `open` で bundle 起動して計測:

- **Round 1（キャプチャ成立）= PASS**: 許可後 `SCShareableContent::get()` 成功、`audio callbacks≈50/s`・
  `frames/elapsed≈47.7k ≈ 48000`（48kHz 連続・format honored）・`peak RMS=0.36`（非無音）。WAV に読み上げ音声を確認。
  → **未署名(ad-hoc) `.app` でシステム音声を実機キャプチャできる**。Rust `screencapturekit` v8 が end-to-end で動作。
- **TCC 帰属・ペイン**: 許可ダイアログは **"MojirokuSpike.app" を名指し**（Terminal ではない）＝`open` で bundle 帰属が正常。
  タイトル "Screen Recording"、一覧ペインは **"Screen & System Audio Recording"**（想定どおり画面収録カテゴリ）。
- **Round 2（再ビルド=新 cdhash 後）= 権限失効は検出可能**: `get()` が **明示エラー**（`NoShareableContent: declined TCCs`）で落ちる
  ＝**起動時の権限失効**はアプリが検出でき、再プロンプトも出る。ただし System Settings の旧エントリは **"stale ON"**（トグル ON のまま実際は未認可）。
- ⚠️ **ただし `get()` 成功＝録れている、ではない（自データが反証）**: Round 1 **初回**は `get()` 成功・`audio callbacks=1251`・
  ストリーム生存でも **`peak RMS=0.00000`（全ゼロ PCM）**だった（このときは単に無音だったが、26.5 で報告のある「会期中に全ゼロ化」/
  Sequoia 月次再認証の失効も**同じ見え方**）。**この会期中の無音化は `get()` では検出不能**で、**RMS レベル検出だけが捕まえられる**。
  しかも全ゼロでも**コールバックは発火する**ので「コールバック無し」検出では不十分＝**レベル(RMS)ベースのウォッチドッグが必須**。
- **再許可コスト**: トグル off/on では戻らず、**「−」削除→「＋」再追加（GUI のみ・ターミナル不要）**で復帰しキャプチャ再開（RMS 0.36）。
  → 更新（新 .dmg=新 cdhash）ごとにテスターは GUI で remove/re-add が要る＝**中程度の摩擦**（stale ON が紛らわしい）。

## 計測結果②（本体アプリでの実機検証 2026-06-27）

Increment 1（`src-tauri` インプロセス実装）を **release バンドル `mojiroku.app`（本番 bundle id `com.daichi0812.mojiroku`）** で検証:

- ✅ TCC ダイアログは **"mojiroku.app" を名指し**（spike と別 bundle id でも bundle 帰属が正常）、ペインは "Screen & System Audio Recording"。許可反映に **Quit & Reopen**（macOS 標準）。
- ✅ 許可後にキャプチャ成立、**WAV を `afplay` で再生して相手音声が明瞭**＝planar/interleaved ダウンミックス正当（spike から残っていた「ダウンミックス明瞭か」の最後の穴を closed）。
- ✅ `Info.plist`（`NSScreenCaptureUsageDescription`）は Tauri v2 が `src-tauri/Info.plist` から**バンドルへマージ**することを実機 plist で確認。release リンクも screencapturekit 込みで成功・Swift rpath 焼込確認。
- ⚠️ **新発見: "private window picker のバイパス" 同意ダイアログ**（"mojiroku is requesting to bypass the system private window picker and directly access your screen and audio"）。macOS 15(Sequoia)+ が、**システムの共有ピッカー UI を介さずプログラム的に `SCStream` を起動するアプリ**に課す追加同意。Allow で正常進行（"システム音声 録音中" に遷移）。
  - ADR の「会期中/定期の再同意」懸念の実機具現。Sequoia 初期は週次→以降緩和だが**アプリ更新（cdhash 変化）で再提示**されうる＝未署名の再ビルド摩擦に上乗せ。→ **RMS ウォッチドッグの必要性を再補強**し、**Developer ID 署名（安定 cdhash）が再提示を減らす**根拠を一段強める。
  - 回避策: `SCContentSharingPicker`（システム共有ピッカー）に切替えるとこの同意は不要だが「毎回共有対象を選ぶ」別摩擦が出る。**プログラム的キャプチャ＋同意**（Granola 等と同型）を既定とし、ピッカーは要検討項目（Increment 2+）。

## まだ de-risk できていない（実装時に検証・スパイクのブロッカーではない）

- **実会議の互換**: 計測は `say`（システム音声）で実証。Zoom/Meet/Teams 実通話は同じシステム音声経路なので低リスク
  （SCK は Teams でも実績あり＝tap の Teams 無音問題は SCK には当たらない）が、実装時に実通話で一度確認する。
- **マイク＋システム音声の同時取得**と **2 つの独立キャプチャクロックのドリフト**（長尺で時刻整合が崩れる）＝**第 2 の未検証リスク**。
  整合は sample-count でなくホスト時刻（mach_absolute_time / presentation timestamp）でスタンプする設計が要る。
- **dev-loop $0 緩和**（無料 Apple Development/Personal Team ID で再ビルド失効を回避できるか）は未計測。ローカル反復用、配布には無関係。
- **Mic + Screen Recording の TCC を同時に**: スパイクは Screen Recording 側のみ検証。実アプリはマイク（自分）と画面収録（相手）の**2 つの TCC 許可を同時に**要する（Microphone TCC + `NSMicrophoneUsageDescription`）。未検証。
- **隔離属性(quarantine)→初回 TCC プロンプトの相互作用**: スパイクはローカルビルド（隔離なし）。配布 .dmg は `xattr -dr com.apple.quarantine` 後に初回 TCC が正常に出るか未検証（既存「damaged」手順と合流する点）。
- **エコー（スピーカー運用）でマイクに相手の声が混入＝帰属を汚す**: mic トラックを無条件「あなた」とラベルするため、ユーザがヘッドホン無し（スピーカー出力）だと mic が相手の声も拾い、相手発話が「あなた」に誤帰属する。デュアルトラックの「ソース帰属＝話者」という前提を実環境で崩す唯一の経路。**実機検証はヘッドホン（クリーン）とスピーカー（混入を確認）の両方で**行い、混入が出たら「diarization が悪い」ではなく音響エコーと切り分ける。対策候補（後日）: ヘッドホン推奨の明示／system トラックとの相関で mic 側の重複区間を抑制／エコーキャンセル。

## 設計上の含意（実装へ申し送り）

- **検出は2層に分ける（自データが示す通り `get()` だけでは穴がある）**:
  - **起動時の権限失効** → `get()` のエラーで検出可能 → 会議開始前に権限プリフライト、失敗時は「システム音声の許可が必要（更新後は再許可が要る）」
    UI ＋ System Settings を開くボタン ＋ **"一覧から削除して再追加"** の手順提示。
  - **会期中の無音化（全ゼロ PCM／月次失効）は `get()` では検出不能** → **RMS レベルベースのウォッチドッグが load-bearing（必須）**。
    全ゼロでもコールバックは発火するので「N 秒コールバック無し」では不十分 ── **「N 秒 RMS≈0」**で検出する。
    ただし**会議中の自然な無音と区別**が要る（例: しきい時間を長め＋"音声を検出していません" の受動表示に留め、誤警報を避ける）。録り逃しは会議アプリで致命なので、この警告系は飾りでなく中核要件。
- Swift Concurrency ランタイムの `.app` 同梱 or OS 解決（rpath 知見・上述）。
- **合成はトラック別 STT＋ソース合成**（システム音声=相手／既存 cpal マイク=自分）。ソース帰属が構造上保証されるため**クロックドリフトに免疫**（drift は近接する異トラック発話の並び順をわずかに乱す程度＝仕上げ）。mic は単一話者で話者分離不要、system のみ任意で sherpa-onnx 分離。2×whisper は Metal で直列＝v1 許容。→ 下記「第 2 リスク（2クロックドリフト）」は**ブロッカーから仕上げに降格**（後日 cheap な実測スポットチェックで cosmetic 域を確認）。サンプルレベル mixing は drift で音が壊れるため採らない。
  - Update 2026-09-05 (Issue #65): the start offset δ between the two tracks is now measured at capture time (first audio callback of each track), stored on the recording as `mic_offset_ms`, and applied before the merge sort and as leading silence in the playback mix. Clock drift is still uncorrected.
- **ライブ文字起こし（増分C, `src-tauri/src/live_stt.rs`）は使い捨てプレビュー**（2026-10 更新: 表示した字幕は停止時に録音と一緒に保存する。権威データは引き続き停止時の文字起こし。[ADR-0048](ADR-0048_Save_the_live_transcript_next_to_the_final_transcript.md)）。ワーカースレッドが mic＋system の直近 mix を ~3.5s ごとに whisper にかけ、確定接頭辞を commit するスライディングウィンドウ方式（ラベル無し＝帰属は停止時のデュアルトラック結果が権威）。VAD＋RMS 二段ゲートで無音ハルシネーションを抑止、drain でメモリ一定、最終パス前に必ず join（whisper を同時に2つ持たない）。**隔離は best-effort で、正直に言えば完全ではない**: `catch_unwind` は **Rust の panic は呑むが、whisper（C++）内部の abort/segfault は防げない** ── これはプロセスごと（＝録音中のセッションごと）落とす。停止時パスも同じ whisper を信頼しており入力は通常 PCM なので**低確率・v1 許容**だが、「録音経路を絶対に巻き込まない」とは言い切れない（完全隔離は whisper のサブプロセス化が要るが使い捨てプレビューには過剰）。また会議中は whisper 常駐（~600MB+）が全録音 RAM バッファに上乗せされ、既知の長尺（2h）メモリ天井を圧迫する（フォローアップ）。
- **増分C は検証視点では「リグレッションゲート」**: キャプチャ経路（直前に実機 PASS したデュアルトラック保存）に毎 ~3.5s の Metal whisper を足す唯一の増分。GPU 競合でキャプチャ音声が glitch すれば保存品質が静かに劣化しうる。実機検証は **(a) 保存文字起こし/音声が C 前と同等にクリーン（あなた/相手の帰属・音飛び無し、保存 `<id>.wav` を実聴）を最優先**、次に (b) ライブ表示が出る、(c) 触った mic.rs/共有 system_audio ヘルパ経由でマイク単独録音・ファイル取り込みが従来通り保存、の順で確認する。

## $99 署名（ADR-0011）への影響 ── 据え置き（ただし広め配布で前倒し根拠が増えた）

- 計測は **(c) サイレント拒否ではなく、検出可能な再プロンプト**だった → **未署名のまま技術ベータ（友人・研究室）は実用可**。
  $99 は **ADR-0011 のまま据え置き**（広め配布・非技術ユーザーの段で判断）。
- ただし **更新ごとの GUI remove/re-add 摩擦**（＋ stale ON の紛らわしさ）は実コスト。**Developer ID 署名は安定 DR を与え
  更新を跨いで許可が残る**（再許可不要）→ notarize は別途「damaged」隔離も解消する twofer。
  **会議モードの存在は「広め配布の段で署名する」根拠を一段強める**（非技術ユーザーに remove/re-add は無理）。

## Consequences

- 実装は **ScreenCaptureKit インプロセス Rust**（`src-tauri`・`mic.rs` の隣）で進める。Plan B（Core Audio tap）は不要（SCK で成立）。
- 上記「設計上の含意」（権限プリフライト＋再許可ガイド UI、**RMS ウォッチドッグ**、Swift ランタイム同梱、デュアルトラックのホスト時刻整合）を実装スコープに含める。
- スパイクハーネス `spikes/meeting-audio/` は本 ADR の一次データとして保持（throwaway だが計測再現用）。
